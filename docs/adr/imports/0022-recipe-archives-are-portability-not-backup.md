# Recipe Archives are portability, not backup

Norish exports recipes as a Recipe Archive — a `.norishrecipes` zip holding a manifest and one folder per recipe with its media inside, read back through the same archive-import loop that already reads Mela, Paprika, Mealie and Tandoor. The feature could have been a backup: preserve ownership, carry accounts, restore an instance somewhere else. **It is an exchange of recipe content instead: importing an archive makes the importer the owner of everything it creates, and nothing about identity travels beyond display-name attribution and the exporter's own rating and favourite mark.** Emails are stored encrypted precisely so they do not leak, and an archive is a file people hand to friends, so no PII rides inside — which is also why the archive scope is simply "everything the exporter can see" under the deployment's view policy, admin scope included, with no privileged extra data behind the admin button. Cuisine names travel as words and attach only where the receiving instance's curated vocabulary already has them (matched case-insensitively): unmatched names are dropped visibly in the import result, never created — any importer could otherwise extend a vocabulary the administrator owns (ADR-0012) — and never demoted to tags, a direction the tag→cuisine migration cleaned up once already. Provenance gaps left by dropped cuisines are Recipe Enrichment's to refill under the target instance's own rules (ADR-0018). The Norish parser inherits the shared import loop's semantics unchanged — match by URL or name within household scope, overwrite on match, freshly minted IDs otherwise; archive IDs are folder keys, never reused. Rejects: ownership-preserving restore with account matching (a different, bigger feature that would drag PII, account-matching and conflict semantics into an exchange format); auto-creating or tag-demoting unknown cuisines; a skip-on-match special case that would make Norish's own format behave unlike every other archive in the same importer; and a background job producing server-side export artifacts — the archive streams straight to the client and never exists on the server at all.

## Consequences

- The container is effectively frozen the day archives exist in the wild — people keep export files for years. The manifest carries `formatVersion: 1` and positive format identification; evolution within a major is additive, and a future importer refuses or adapts to a newer major instead of guessing.
- An admin's instance-wide export is the same operation with admin scope, so importing it elsewhere lands every recipe under the one importing user (or overwrites their matches). That flattening is the accepted cost; instance migration would be its own feature, and this is deliberately not it.
- Overwrite-on-match means importing a stale archive replaces edits made since it was written. Consistency with every other archive format was chosen over edit protection; protecting edits would mean changing the shared loop for all formats, not special-casing this one.
- Streaming delivery means a long download for video-heavy instance exports. Moving to a job-built artifact later is additive and does not touch the format.
- Recipe Archive is product language and lives in `CONTEXT.md`; the container layout (manifest, per-recipe folders, relative media paths) is implementation and does not.
- Amended 2026-10-14, after a Recipe Keeper archive of 488 recipes held six different recipes sharing a name with another in the same file, each of which would have overwritten its twin: a name match no longer wins where both recipes carry a URL and the URLs differ, and a recipe the running import has already written, inserted or overwritten, is matched by URL only, so an archive never overwrites its own recipes by name (remembering only the ones it created would still let a second same-named entry overwrite the first where both matched a recipe already in the library). Exact copies (same URL) still collapse into one. The shared loop applies this to every format it reads.
- Amended 2026-10-14: cookbooks travel as titles, reversing "cookbooks stay behind". Each recipe in an archive names, by title, every cookbook the exporter can see that holds it; importing files the recipe into the importer's own cookbook of that title (matched case-insensitively, trimmed), making one where none exists, and a re-import only ever adds memberships. Cover images and cookbooks holding no exported recipe stay behind. An archive is still content, not a Library: a cookbook title is something a recipe is filed under, as a foreign app's collection is, and a Recipe Keeper archive brings its collections in on the same path. The field is additive within `formatVersion: 1`, so an older importer ignores it. Rejected: a manifest-level cookbook list carrying covers and empty cookbooks, a second import path only Norish would use, for a cover the receiving instance draws from the members anyway.
